# ERP 模块公共工具包应用审计报告

**审计日期**：2026-05-01
**审计目标**：评估 `com.ruoyi.erp` 对 `com.ruoyi.common`（ERP专属公共工具包）的利用程度，识别遗漏、重复造轮子、该用未用的情况。

## 三、严重遗漏（该用未用，且 ERP 自行低水平重复实现）

### 遗漏 1：JdbcExecutor —— 整个 JDBC 操作体系的缺失

**common 提供的价值**：
```
JdbcExecutor
  - selectList(sql, params) → List<Map>
  - selectPage(sql, params, pageNum, pageSize) → PageResult
  - insert(table, data) → int
  - update(table, data, where) → int
  - delete(table, where) → int
  - batchInsert / batchUpdate
  - 内置事务管理
```

**ERP 现状**：每个 ServiceImpl 都直接注入 `JdbcTemplate`，手工拼接 SQL + 手工分页 + 手工类型转换。

| 文件 | 手工做法 | 行数 |
|------|---------|------|
| ErpPageConfigServiceImpl | 7 处 `new StringBuilder("SELECT * FROM ...")` | ~200 行 SQL 构建 |
| ErpApprovalFlowServiceImpl | 4 处手工 SQL 构建 + IN 子句拼接 | ~80 行 |
| ErpPushRelationServiceImpl | 4 处手工 SQL + IN 子句拼接 | ~80 行 |
| SuperDataPermissionServiceImpl | `String.format("INSERT INTO %s (%s) VALUES (%s)")` | ~140 行 |
| DynamicQueryEngine | 直接 JdbcTemplate.query() | ~50 行 |

**结论**：5 个核心服务类各自实现了一套 JDBC 操作模式，总计约 550 行重复的 SQL 构建和结果处理逻辑，完全可以用 `JdbcExecutor` 统一。

---

### 遗漏 2：SqlSecurityValidator —— SQL 安全校验形同虚设

**common 提供的价值**：
```
SqlSecurityValidator
  - validateIdentifier(name) → 校验表名/字段名合法性
  - validateSql(sql) → 检测危险关键字
  - containsDangerousKeyword(sql) → SQL注入检测
  - getValidIdentifiers(tableName) → 白名单模式
```

**ERP 现状**：
- `DynamicQueryEngine` 接收前端传入的 `searchConfig.fields`，其中的 `field` 值经 `SqlBuilder.buildWhere` 拼入 SQL，但从未调用 `SqlSecurityValidator` 校验
- `ErpRelationController` 直接拼接 `@RequestParam String table` 到 SQL
- `SuperDataPermissionServiceImpl` 动态拼接表名 `String.format("INSERT INTO %s ...", tableName)`，表名来自外部参数

**结论**：common 已提供完整的 SQL 安全校验工具，ERP 模块存在多处动态 SQL 拼接却完全未使用。这是安全层面的严重遗漏。

---

### 遗漏 3：DataScopeInjector —— 数据权限注入器闲置

**common 提供的价值**：
```
DataScopeInjector
  - injectDataScope(sql, moduleCode) → 在WHERE中注入部门/角色数据过滤
  - getDeptFilterCondition() → 获取当前用户的数据权限条件
```

**ERP 现状**：`SuperDataPermissionServiceImpl` 手工实现了 `selectPageByModuleWithTableName`，在 SQL 中手动拼接 `dept_id IN (...)` 条件，逻辑与 `DataScopeInjector` 高度重合但实现方式各异。

**结论**：数据权限注入是 ERP 核心功能，common 已提供标准方案却未被使用，导致每个需要数据隔离的业务模块都要重复开发。

---

### 遗漏 4：CommonCrudEngine —— 通用CRUD引擎闲置

**common 提供的价值**：
```
CommonCrudEngine
  - query(tableName, conditions, pageQuery) → 分页查询
  - getById(tableName, id) → 单条查询
  - create(tableName, data) → 新增
  - updateById(tableName, id, data) → 更新
  - deleteById(tableName, id) → 删除
  - 内置: 字段白名单过滤、SQL安全校验、数据权限注入
```

**ERP 现状**：`ErpPageConfigServiceImpl`、`ErpApprovalFlowServiceImpl`、`ErpPushRelationServiceImpl`、`SuperDataPermissionServiceImpl` 四个类各自实现 CRUD，每个都手工处理字段过滤、条件拼接、分页封装。

**结论**：`CommonCrudEngine` 是专门为 ERP 低代码架构设计的通用 CRUD，集成了白名单、安全、权限三大能力。目前完全闲置，4 个 ServiceImpl 各自重复实现。

---

### 遗漏 5：IdGenerator —— 雪花ID被SQL函数替代

**common 提供的价值**：
```
IdGenerator
  - nextId() → 64位雪花ID（时钟回拨保护）
  - generateCode("ORD_") → "ORD_7234567890" 带前缀业务编码
```

**ERP 现状**：SQL 脚本中 `fn_snowflake_id` 函数被定义了 4 次，算法各不相同（毫秒级 vs 秒级时间戳），且存在同一秒 ID 重复风险。

**结论**：Java 侧 `IdGenerator` 提供了标准的雪花算法 + 时钟回拨保护，但 ERP 模块在 Java 代码中完全不生成 ID，依赖 SQL 脚本中不一致的自定义函数。应在 Service 层调用 `IdGenerator.generateCode()` 统一生成业务编码。

---

### 遗漏 6：JsonUtil —— JSON 处理两套并存

**common 提供的价值**：
```
JsonUtil (基于 Jackson, 300+ 行)
  - toJson / fromJson / fromJsonList
  - toMap / toListMap
  - isValid(校验) / extractField / extractNestedField
  - deepCopy / convert / mapToObject
```

**ERP 现状**：`ConfigParser` 直接使用 `com.alibaba.fastjson2.JSON` 处理 JSON，`ErpPageConfigServiceImpl` 则混用 `JsonUtils`（ruoyi框架）和 `JsonUtil`（common，仅在 versionDiff 等方法中用到）。

**结论**：项目中同时存在 fastjson2、Jackson(JsonUtil)、ruoyi-JsonUtils 三套 JSON 处理方式。应统一为 `JsonUtil`（common提供），消除 fastjson2 直接依赖。

---

### 遗漏 7：SimpleCache —— 字典缓存自己造轮子

**common 提供的价值**：
```
SimpleCache<K, V>
  - put(key, value, ttlSeconds)
  - get(key) → V（自动过期检测）
  - remove / clear / size
  - 线程安全（ConcurrentHashMap + 惰性过期）
```

**ERP 现状**：`DictionaryBuilderEngine` 内部使用 `ConcurrentHashMap<String, DictionaryCache>` 自行管理缓存，但缺少 TTL 支持、缺少 LRU 淘汰、缺少统计监控。

**结论**：`SimpleCache` 提供了带 TTL 的线程安全缓存，`DictionaryBuilderEngine` 应改为包装 `SimpleCache` 而非从零实现。

## 六、改进优先级

### P0 —— 安全相关，必须立即修复

| # | 事项 | 影响 |

| 1 | 所有动态 SQL 拼接处接入 `SqlSecurityValidator` | 防止 SQL 注入 |

| 3 | `ErpRelationController` 的表名参数改用 `SqlSecurityValidator.validateIdentifier()` | 防止表名注入 |

## 七、总结

ERP 模块仅使用了 `com.ruoyi.common` 公共工具包 45 个类中的 5 个（**11%利用率**），其余 40 个类完全闲置。核心问题：

1. **整个 JDBC 操作体系（JdbcExecutor + CommonCrudEngine + SqlSecurityValidator + DataScopeInjector）完全被绕过**，每个 ServiceImpl 自行实现 CRUD，产生约 550 行重复 SQL 构建代码，且缺少安全校验
2. **ID 生成、JSON 处理、缓存管理、数据校验四大场景全部自行造轮子**，与 common 现有实现功能重叠
3. **公共工具包的设计意图（统一SQL安全、统一CRUD、统一数据权限）在 ERP 模块中落空**

**建议**：按 P0 → P1 → P2 顺序逐步收敛。P0 聚焦安全接入（3项），P1 消除核心重复（6项），P2 规范统一（5项）。完成后 ERP 模块可删除约 1300 行重复代码，并将 common 利用率从 11% 提升至 60%+。
